# Vendor stack — a reference system under test

A dataspace stack for the Verification Environment (VE) to verify: an **externally hosted**
participant, reachable only over DSP, DCP and the certificate exchange (DSAF SCE), exactly as
[docs/sut-verification.md](../docs/sut-verification.md) expects of a third-party solution.

It is built from the VE's own components — the Core Platform Distribution, the DECADE-X profile
seeding, Certo and the Certo CFM agent, at the versions `charts/cx-ve` pins — and runs in its
**own kind cluster**, next to the VE. There is one stack per dataspace; DECADE-X is the only one so
far, and every script takes `-d decade-x` (the default). So it proves the VE's side of the wire
end to end, not interoperability with a foreign implementation: that is the next step, with a
different vendor's connector and wallet in this stack's place.

None of the VE's applications (onboarding API, Membership Hub, Verification UI, Compliance
Tracker) run here. What a vendor does with its own tooling is scripted in [`scripts/`](scripts).

## Topology

| | VE | vendor stack |
|---|---|---|
| kind cluster | `cxve` (`~/.kube/cxve.config`) | `dx-vendor` (`~/.kube/dx-vendor.config`) |
| release | `cx-ve` | `vendor-stack` |
| gateway | `http://cxve.localhost` (port 80) | `http://dx-vendor.localhost:8081` |
| participant DID | `did:web:identity.cxve.localhost:verification-participant-dx` | `did:web:identity.dx-vendor.localhost%3A8081:vendor-participant` |
| member id | DECADE-X-ID generated by the Membership Hub | DECADE-X-ID assigned by the TSP on approval (`DX-00009001` until then) |
| issuer DID | `did:web:issuer.cxve.localhost:issuer` | `did:web:issuer.dx-vendor.localhost%3A8081:issuer` (issues nothing) |
| trusts | its own issuer | its own issuer **and the VE's** |
| DSP profile | `decade-x` | `decade-x` |

**Why the port is in the DIDs.** The VE's cluster holds port 80 on the host, so the stack's
gateway is on 8081 — and the platform advertises the port (`global.external.port`) in every URL
and DID. That makes one address work from every place that dereferences it: the host (kind port
mapping), the stack's own pods (CoreDNS rewrite to the Traefik Service, exposed on that port) and
the VE's pods (CoreDNS `hosts` entry to the stack's node IP, where Traefik binds that port as
hostPort).

**Transfers follow the Data Plane Signaling HTTP transfer profile.** Both certificate-exchange
flows are pull transfers of type `https://w3id.org/dspace-sig/profile/http-pull` — the
[transfer profile](https://eclipse-dataplane-signaling.github.io/profiles/HEAD/#transfer-profiles)
value, which is also the `endpointType` of the DataAddress the data plane hands out. Assets carry
no address of their own: the participant's data-plane mapping points that transfer type at Certo.
(The profile requires HTTPS endpoints; like the VE, this stack runs HTTP only.)

**Why nothing in this stack issues credentials.** The participant is provisioned without CFM's
credential activities (`chart/templates/certo-activity-seed-job.yaml`). Its credentials come from
the VE: onboarding the participant in a verification run has the VE's onboarding API (the TSP)
register the DID as a holder with the VE's issuer once it approves the request, the issuer sends a
DCP credential offer, and IdentityHub requests the offered credentials by itself. A credential
from this stack's own issuer would not merely be redundant — the VE does not trust that issuer,
and one untrusted credential makes the VE reject the whole presentation.

## Deploying the vendor stack

The block below deploys the stack and runs one verification against it;
[Step-by-step](#step-by-step-verifying-the-vendor-stack) explains every command. All commands run
from the repository root.

```shell
./scripts/install-ve.sh                         # the VE, unless it is already running
./vendor-stack/install.sh                       # cluster dx-vendor, http://dx-vendor.localhost:8081
./vendor-stack/connect.sh
./vendor-stack/scripts/create-participant.sh    # the TSP assigns the DECADE-X-ID on approval
./vendor-stack/scripts/seed-ccm-offer.sh

# verify it: start a run, then issue + notify the certificate (it waits for the run's credentials)
curl -s -X POST http://cxve.localhost/ui/api/runs -H 'Content-Type: application/json' \
  -d '{"dataspace":"decade-x","useCase":"ccm","name":"Vendor Participant",
       "did":"did:web:identity.dx-vendor.localhost%3A8081:vendor-participant"}' | jq -r .id
./vendor-stack/scripts/push-certificate.sh
./vendor-stack/scripts/status.sh                # the exchange as the vendor sees it
```

What follows from the dataspace:

| | DECADE-X |
|---|---|
| member id | DECADE-X-ID — assigned by the VE's onboarding API (the TSP) when it approves the run's onboarding, so the run form takes none; `-m` (default `DX-00009001`) only provisions the Certo tenant until then |
| credentials from the VE | `dx:DX_LegalEntity_VC` (`credentialSubject.partner`: the legal entity, its `partnerID` the DECADE-X-ID) and `dx:DX_Site_VC` (`partner`: the first business site) |
| DSP profile | `decade-x` — its DCP scope asks for the `dx:DX_LegalEntity_VC` |
| offer policies | none yet — no DECADE-X policy vocabulary exists |
| VE counterparty | `…:verification-participant-dx` — Certo addresses it by DID; its DECADE-X-ID (generated by the Membership Hub) is not needed |

A DID document advertises ONE DSP profile per platform, so `push-certificate.sh` replaces the
profile segment of the VE verification participant's advertised endpoint with the stack's; the
stack itself advertises `decade-x`, which is the endpoint the VE dials.

## Step-by-step: verifying the vendor stack

Times are rough figures for a local machine.

### 0. Prerequisites

- `docker`, `kind`, `helm`, `kubectl`, `curl`, `jq`
- the Traefik chart repository: `helm repo add traefik https://traefik.github.io/charts`
- host ports free: **80** (VE), **8081** (vendor stack)
- room for full platforms — the VE and the vendor stack use about 9 GB of memory together

### 1. Install the VE (≈ 15 min)

```shell
./scripts/install-ve.sh
```

Recreates the `cxve` cluster, builds the VE's applications and installs them with the platform.
Done when the output ends with `DID DNS setup verified for cluster 'cxve'.` — the Verification UI
is then at <http://cxve.localhost/ui>.

Skip this step if the VE is already running on core platform ≥ 0.0.29.

### 2. Install the vendor stack (≈ 5 min)

```shell
./vendor-stack/install.sh
```

Recreates the stack's cluster (an existing one is deleted) and installs the stack, seeding the
`decade-x` DSP profile with the VE's issuer trusted, and the Tenant Manager's DECADE-X dataspace
profile participant provisioning needs. Done when it prints `Vendor stack (decade-x) is up`.
Check that its identity carries the port:

```shell
curl -s http://issuer.dx-vendor.localhost:8081/issuer/did.json | jq -r .id
# did:web:issuer.dx-vendor.localhost%3A8081:issuer
```

### 3. Connect the stack to the VE (≈ 2 min)

```shell
./vendor-stack/connect.sh
```

Points each cluster's DNS at the other's gateway, then fetches each side's issuer DID document from
a pod on the other side. Done when it prints `Connected: cxve <-> dx-vendor`. The stack's entries
in the VE's DNS are tagged with its cluster name, so connecting another stack leaves them in place.

Re-run this after re-installing either cluster, and after a docker restart.

### 4. Create the vendor participant (≈ 1 min)

```shell
./vendor-stack/scripts/create-participant.sh
```

Provisions the participant (control plane, wallet, DID document, data plane, Certo tenant) and
prints what the VE needs to know about it:

```
Vendor participant provisioned (decade-x).
  DID:                  did:web:identity.dx-vendor.localhost%3A8081:vendor-participant
  DECADE-X-ID:          DX-00009001 (provisional — the TSP assigns it on approval)
  participant context:  <participant context id>
  DID document:         http://identity.dx-vendor.localhost:8081/vendor-participant/did.json
  DSP endpoint:         http://dx-vendor.localhost:8081/api/dsp/<participant context id>/decade-x
```

Its wallet is empty at this point — `scripts/status.sh` shows `none — the VE has not delivered any`.

A different name, short name or provisional member id: `-n`, `-s`, `-m`. The short name is the
last DID segment and identifies the participant to every other script, so pass the same `-s` to
`seed-ccm-offer.sh`, `push-certificate.sh` and `status.sh` — and enter the matching DID in step 6
(only the DID: the TSP assigns the DECADE-X-ID).

Re-running the script for an existing short name reuses that participant and says so; it fails if
`-n` or `-m` differ from the existing participant's. Only a new `-s` creates another participant.

### 5. Seed the certificate offer

```shell
./vendor-stack/scripts/seed-ccm-offer.sh
```

Creates the certificate offer the VE's verification participant will negotiate: an asset
declaring the SCE Certificate Provider API (`dct:conformsTo`
`https://w3id.org/dsaf/sce/v1/provider-api`, the IRI that names both the API and the SCE major
version), its policies and contract definition. The VE finds the offer by that property, so the
asset id is free — by default `<short name>-ccm-provider-api`. SCE has a participant publish one
dataset per API, and a run fails when the catalog offers it twice. Can run any time after step 4.

The policies mirror the VE's own offers in the dataspace: unconstrained, but the `decade-x`
profile still requires the consumer to present its `dx:DX_LegalEntity_VC`.

### 6. Start a verification run on the VE

In the Verification UI (<http://cxve.localhost/ui>), pick **DECADE-X** and **Company Certificate
Management**, then under **Start a verification run** enter the participant DID
`did:web:identity.dx-vendor.localhost%3A8081:vendor-participant`. No member id is asked: the TSP
assigns it when it approves the run's onboarding, and the run shows it from then on. Name and
short name are disabled once a DID is entered: the participant is named by its own system. Then
**Start verification run**. The same from the command line:

```shell
curl -s -X POST http://cxve.localhost/ui/api/runs -H 'Content-Type: application/json' \
  -d '{"dataspace":"decade-x","useCase":"ccm","name":"Vendor Participant",
       "did":"did:web:identity.dx-vendor.localhost%3A8081:vendor-participant"}' | jq -r .id
```

The run opens with its step list. On a fresh VE, the first step onboards the VE's own verification
participant, which takes a minute or two.

### 7. Issue and notify the certificate

```shell
./vendor-stack/scripts/push-certificate.sh
```

Can run any time after step 4 — before or after starting the run. It waits by itself: for the VE's
verification participant (on a fresh VE a run creates it first), for the credentials the run
delivers (logging `no dx:DX_LegalEntity_VC in the wallet yet`), then for the VE's inbox offer —
the dataset declaring the SCE Certificate Consumer API (`dct:conformsTo`
`https://w3id.org/dsaf/sce/v1/consumer-api`), only visible to a participant holding the VE-issued
credentials. Along the way it

1. issues an `iso9001` certificate in the vendor's Certo, certifying the vendor's legal entity
   under the DECADE-X-ID the TSP assigned (the vendor's `dx:DX_LegalEntity_VC`,
   `partner.partnerID`) — from then on Certo fulfils the run's request for it on arrival;
2. negotiates the inbox offer, opens the push flow and notifies the verification participant that
   the certificate is `AVAILABLE`;
3. fulfils the run's request if it arrived before the certificate existed and still waits, pushing
   `FULFILLED` to the verification participant.

```
Certificate issued and handed to the verification participant.
  certificate:  97d75e5e-… revision 0 (iso9001, holder DX-…)
  notified:     did:web:identity.cxve.localhost:verification-participant-dx (AVAILABLE)
  exchange:     none was waiting — the run's request is fulfilled on arrival; its exchange id is on the VE run (and status.sh)
```

When the run had already requested the certificate, `exchange:` names the exchange the script
fulfilled instead.

A run needs it at most once: a later run's request is fulfilled from the certificate already held
(see step 9). A rerun is harmless — it issues and notifies another certificate, and notifications
never open or change an exchange.

### 8. Watch the run finish

Each step and whose move it is:

| Step (UI label) | Who acts | What happens |
|---|---|---|
| Ensure verification participant | VE | its consumer participant exists, with its inbox offer |
| Resolve participant DID | VE | fetches the vendor's DID document from inside its cluster |
| Onboard participant | VE | onboards the DID into the dataspace and registers it as a credential holder |
| Offer credentials | VE | its issuer sends a DCP credential offer to the vendor's wallet |
| Await credential delivery | **vendor** | the wallet requests the credentials; the issuer delivers them |
| Establish pull flow | VE, needs step 5 | finds the provider API offer, negotiates it, starts the transfer |
| Request certificate | VE, answered by the **vendor** (step 7) | requests an `iso9001` certificate for the vendor's DECADE-X-ID over the pull flow: `FULFILLED` proceeds; `RECEIVED` polls the vendor until it is `FULFILLED` (step 7), within the fulfillment timeout; `DECLINED` fails the run |
| Retrieve & verify document | VE | pulls certificate and document over the pull flow |
| Accept certificate | VE | records ACCEPTED and reports it back to the vendor |

The run ends **SUCCEEDED**. The vendor's side of the same exchange:

```shell
./vendor-stack/scripts/status.sh
# == credentials
#    dx:DX_LegalEntity_VC from did:web:issuer.cxve.localhost:issuer (state 500)
#    dx:DX_Site_VC from did:web:issuer.cxve.localhost:issuer (state 500)
# == certificate exchanges
#    56ff34a5-… iso9001 from did:web:identity.cxve.localhost:verification-participant-dx at …: FULFILLED, acceptance ACCEPTED
```

`status.sh --exchange <exchange id>` (the id the run shows) prints one exchange in full.

### 9. Run it again

Nothing needs reinstalling: repeat **step 6** (the run adopts the existing membership — its
"Onboard participant" step says `adopted` — and the credentials are already there). Step 7 is
optional: the certificate it issued before is still held (Certo keeps it in the stack's Postgres
until the stack is re-installed), so Certo fulfils the new run's request on arrival; rerun it to
issue and notify a fresh one.

### Tear down

```shell
kind delete cluster -n dx-vendor   # the vendor stack
kind delete cluster -n cxve        # the VE
```

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `connect.sh` prints `FAIL` for a peer check | a cluster was re-installed or docker restarted, node IPs changed | re-run `connect.sh` |
| run fails at "Resolve participant DID" | the VE cannot resolve the vendor's hostnames | re-run `connect.sh` |
| run hangs at "Establish pull flow" | no dataset declares the SCE provider API (`dct:conformsTo` `…/sce/v1/provider-api`) — the offer is missing, or was created without the property | `scripts/seed-ccm-offer.sh -s <short name>`; the run picks the offer up while it still waits (15 min). The VE's log names what the catalog does offer |
| run fails at "Establish pull flow": the provider API is offered twice | two assets declare the provider API | delete one — SCE has a participant publish one dataset per API |
| `push-certificate.sh` keeps logging `no ProtocolEndpoint in the DID document … yet` | the VE's verification participant does not exist yet | start a run (or **Ensure participant** in the UI); the script picks it up |
| run waits at "Await credential delivery", `status.sh` shows no credentials | the wallet did not answer the credential offer | `scripts/request-credentials.sh` requests them explicitly |
| a catalog or negotiation request is answered `401`, the control plane logs `Number of requested credentials does not match the number of returned credentials` | the request went to an endpoint of another DSP profile, or the VE predates the `decade-x` profile | re-install the VE, then the stack, and re-run `connect.sh` |
| `push-certificate.sh` logs `catalog request answered HTTP 502 … code=401`; the control planes log `Failed to download status list credential` | a cluster runs core platform < 0.0.29, whose credentials name an in-cluster status list | bump the platform, re-install **both** clusters (credentials keep the URL they were issued with) |
| run fails at "Request certificate" on the fulfillment timeout | the request waited (`RECEIVED`) and nothing fulfilled it — `push-certificate.sh` did not run, or its certificate does not cover the request (it logs `WARNING: exchange … still waits`) | run `push-certificate.sh` while the run waits; `status.sh` lists the waiting exchange |
| run fails at "Request certificate": `DECLINED` | the vendor's Certo declined the request | `status.sh --exchange <exchange id>` shows the grounds |

`scripts/status.sh` is the first stop for anything else: provisioning state, the wallet's
credentials and who issued them.

## Caveats

- **Always install from scratch.** `install.sh` deletes and recreates the cluster; upgrading the
  release in place is not exercised.
- **Ids are per participant.** EDC object ids are unique across all participant contexts of a
  control plane, so the scripts derive every id from the short name — several vendor participants
  can share the stack, each needing its own `-s`.
- **Node IPs are not stable.** `connect.sh` pins each cluster's node address into the other's
  CoreDNS; docker restarts can reassign them.
- **The VE-side DNS entries are managed by `setup-did-dns.sh --sut`**, tagged with the vendor
  cluster's name (`--sut-name`): `connect.sh` replaces only its own stack's entries, so stacks of
  several dataspaces can be connected at once.
- **HTTP only**, like the VE (see docs/sut-verification.md).
- **Core platform ≥ 0.0.29 on both sides.** Earlier versions wrote the issuer's in-cluster status
  list URL into every credential; across clusters that resolves to the wrong issuer, and every
  presentation is rejected with 401. Credentials keep the URL they were issued with, so a platform
  bump means reinstalling both clusters.
